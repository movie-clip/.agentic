## Subject and flow

**Who.** Three people: the owner and two friends, on a laptop most of the time and on a phone sometimes. They know the site and each other; they are not strangers learning a product. **The one job:** get in, or get out, with no doubt about which state they are in. Dense and fast beats pretty (ux.md § Who the screens are for).

**What they see first.** On sign-in, the two fields and the button. In the shell, that they are in the admin area (not on the public site), and whose session it is.

**What exists today** (screenshots 05-product-phone.png and 05-404-desktop.png, run dir `screens/`): a white page, a thin header with the bold site name, an edge-to-edge 1px border, content in one left-aligned column (`--content-width`, 1.5rem sides), blue `#0b5cad` filled buttons, outlined notice boxes with a blue left rule, a text-link footer. No shadows, no motion, one typeface. This spec builds on all of it and adds only what a form and an admin chrome need.

**Flow.**

1. Anonymous request for any admin URL, with no valid session, ends at the sign-in page (D-10). The page shows the "sign-in required" notice. Nothing from the admin area is shown and no cookie is set.
2. The admin types email and password and presses "Iniciar sesión".
3. Wrong or unknown credentials: the same sign-in page again, with one error message, email kept, password cleared. Empty or malformed input: per-field messages.
4. Correct credentials: the admin shell landing (AC 9). It always lands on the shell, never on the page first asked for.
5. In the shell the admin can only read the landing and press "Cerrar sesión". The nav entries beyond "Inicio" are placeholders.
6. "Cerrar sesión" ends the session and lands on the sign-in page with the notice "Has cerrado sesión." (AC 15).
7. After 8 hours the next request is treated as anonymous: step 1 again (D-9).
8. A signed-in admin who opens the sign-in page is sent to the shell.

No other exits. There is no sign-up, no "forgot password" link, no "remember me" and no link to the public site from any admin screen (D-5, D-9, AC 1). No public page links to the admin area (AC 26).

## Admin chrome versus public chrome

**Decision: admin pages do not use the public header and footer** (this was left to the ux lane by the story, § Scope last bullet).

Why: the public footer is three legal links for visitors, and the public header is a link home. Neither helps the three admins, and showing the public chrome on the admin pages would make the two areas look like one product, which is the wrong signal for someone about to approve a feed or hide a product. The sign-in page especially should look nothing like a page a shopper can reach.

What differs, concretely:

| | Public chrome | Admin chrome |
|---|---|---|
| Top edge | none | 0.25rem solid `--color-text` rule across the full width, above everything |
| Brand | site name, bold, a link home | site name, bold, plain text (not a link), then a thin vertical divider and "Administración" in `--color-muted` |
| Right side | nothing | identity and "Cerrar sesión" (signed in only) |
| Navigation | none | a nav bar under the header (signed in only) |
| Footer | three legal links | none |

What is shared: white background, 1px `--color-border` line under the header edge to edge, content in the same `--content-width` column with 1.5rem sides, same type, same focus ring. The admin is the same product with a clearly marked workroom, not a second visual language.

The sign-in page uses the same admin header with only the brand part: no identity, no sign-out, no nav.

Admin header and `.page` main: h1 "Ha ocurrido un error", a muted sentence, and a link "Volver al inicio". If the failure leaves no session to read, the header is the brand-only one.

If the tech lead redirects to sign-in instead, the sign-in page shows its own unavailable error and this screen is not built.

## Accessibility floor

- **Keyboard focus** is a visible 3px `--color-link` ring with a 2px offset on every interactive element: both fields, the sign-in button, the sign-out button and the "Inicio" link. The ring replaces, and never removes, the browser default. Placeholder nav entries take no focus.
- **Focus order, sign-in:** email, password, "Iniciar sesión". Notices and error blocks take no focus. **Shell:** "Cerrar sesión", "Inicio", then the main content; there is no skip link because there is nothing between the header and the content worth skipping. DOM order matches reading order; no positive `tabindex`.
- **Focus after a result:** wrong credentials or service problem: the password field (email if empty). Validation: the first invalid field. Nothing steals focus on first load.
- **Announcements:** the error block is `role="alert"`; notices are `role="status"`; the field messages are tied to their field by `aria-describedby`, and invalid fields carry `aria-invalid="true"`.
- **Landmarks:** `<header>`, `<nav aria-label>` (text from `Chrome.navLabel`), `<main>`; one `<h1>` per page. The header's brand is not a heading.
- **Labels:** every field has a visible `<label>` tied to it. Autofill hints: username (email field), current-password (password field), so password managers work.
- **Contrast:** see § Tokens and components; all text at least 4.5:1, control borders and the ring at least 3:1.
- **Tap targets:** every field, button and nav item at least 44px (`--tap-target`) tall; the sign-in button is full width.
- **Zoom:** form control text at 1rem or more.
- **Reduced motion:** there is no motion, including in the pending state, so no special case.
- **Language:** the page language is Spanish (AC 27).
- **Text alternatives:** no images or icons are used.
- **Not colour alone:** the error state, the current nav entry and placeholders are told apart by words, border weight and underline, never by colour only.
